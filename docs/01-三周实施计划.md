# 视频数据网关 —— 三周实施计划（应届生考核版）

> 定位：公司领导对校招应届生的能力考核，非生产项目。
> 技术栈：Java 17 + Spring Boot 3.3.5 + MyBatis-Plus + MySQL 8 + Vue3/Element Plus
> 环境：Windows 单机（本机开发 + 本机演示），**不依赖 GitHub，全部走国内源**
> 编写日期：第 0 天

---

## 0. 考核定位：考的是什么

领导不会真的期待一个生产级系统。真实评分点（按权重推测）：

| 权重 | 评分点 | 应对策略 |
|---|---|---|
| 高 | 能不能独立跑起来、现场演示成功 | 优先打通"一条线"，准备录屏兜底 |
| 高 | 架构分层是否清晰（媒体层/业务层/台账分离） | 明确三层架构，答辩讲清楚 |
| 中高 | 是否想到考核方没提的东西 | 断流告警、推流鉴权、幂等重试、统计看板 |
| 中高 | 表达与文档质量 | README + 架构图 + 接口文档 + 演示脚本 |
| 中 | 代码规范、异常处理、日志 | 统一返回体、全局异常、traceId |
| 中 | 过程可追溯 | 每日 Git 提交 + 进度日志 |

**核心策略：一条线打穿 + 三个亮点做深 + 全程留痕。功能不在多，在完整、能讲清。**

## 1. 范围基线（先定死，避免失控）

### 1.1 做（P0 必须）

- ZLM 单机接入：RTMP/RTSP 推流 → HTTP-FLV / HLS / WebRTC 播放
- 设备 + 通道主数据管理（CRUD）
- 接收 ZLM Webhook（推流开始/结束、播放开始/结束）
- **业务台账**：事件流水 + 流会话聚合 + 查询接口
- 对外 REST API（统一返回体、分页、参数校验、token 鉴权）
- 一页前端台账（Vue3 + Element Plus）
- 推流鉴权：stream key 不存在则拒绝推流并留痕

### 1.2 做（P1 加分）

- 播放地址签发 + 播放 token 鉴权（on_play 验签）
- 出口 Webhook 推送：HMAC 签名 + 事件ID幂等 + 指数退避重试 + 推送日志
- 录像：开始/停止 + on_record_mp4 落录像台账
- 统计看板：今日推流数 / 在线设备 / 播放次数 / 告警数

### 1.3 明确不做（写进文档，是加分项）

| 不做 | 理由（答辩口径） |
|---|---|
| GB28181 的 SIP 信令（REGISTER/INVITE/Catalog） | 信令层是独立大工程；本期聚焦网关与业务台账，媒体层已具备 GB28181 PS 流接入能力，信令对接列二期 |
| 微服务拆分 / 集群 / 多 ZLM 节点 | 三周内单体更能保证交付质量；架构图保留多节点扩展点 |
| 转码 / AI 分析 / 录像回放拖动 | 非网关核心职责，列为演进方向 |
| 完整 RBAC 权限体系 | 本期用统一 API Token，RBAC 只设计不实现 |

## 2. 系统架构

```
        摄像机 / ffmpeg / OBS / 第三方平台
                    │  RTMP / RTSP / GB28181(PS/RTP)
                    ▼
        ┌───────────────────────────────┐
        │  ZLMediaKit (MediaServer.exe) │  媒体面 data plane
        │  收流 · 转协议 · 分发 · 录像    │  独立进程，绿色运行
        └──────┬────────────────┬───────┘
       REST   │                │  Webhook(HTTP POST 回调)
       (网关→ZLM)              (ZLM→网关)
               ▼                ▼
        ┌──────────────────────────────────────────┐
        │  视频数据网关 (Spring Boot 单体)           │  业务面 control plane
        │  ┌────────────┐  ┌────────────┐          │
        │  │ 接入层      │  │ 台账服务    │          │
        │  │ HookController│ │ LedgerService│        │
        │  └────────────┘  └────────────┘          │
        │  ┌────────────┐  ┌────────────┐          │
        │  │ 对外 API    │  │ 推送服务    │          │
        │  │ RESTful     │  │ Push/Retry │          │
        │  └────────────┘  └────────────┘          │
        └──────┬───────────────────────┬───────────┘
               ▼                       ▼
        ┌────────────┐          ┌──────────────────┐
        │  MySQL 8   │          │ 下游业务系统/前端  │
        │  台账持久化 │          │ (REST 查询+Webhook)│
        └────────────┘          └──────────────────┘
```

**关键认知**：视频流不经过后端代码，后端只处理信令与元数据（JSON），因此单机即可支撑演示。

## 3. 数据模型（8 张表）

| 表 | 职责 | 说明 |
|---|---|---|
| `biz_device` | 设备主数据 | 设备编码、类型、状态 |
| `biz_channel` | 通道主数据 | stream_app / stream_id 为 ZLM 推流标识，1 设备 N 通道 |
| `biz_stream_session` | **流会话（聚合）** | 一次推流的完整生命周期，自动算时长 |
| `biz_ledger` | **业务台账（流水）** | 所有业务事件流水，可追溯 |
| `biz_play_session` | 播放会话 | 观看时长统计 |
| `biz_recording` | 录像台账 | 文件路径、大小、时间段 |
| `biz_webhook_subscriber` | 下游订阅者 | 回调地址 + 密钥 + 订阅事件 |
| `biz_webhook_push_log` | 推送日志/重试队列 | 兼做重试队列，唯一索引保证幂等 |

**设计要点（答辩加分）**
- 流水表 vs 聚合表分离：`biz_ledger` 记"发生了什么"，`biz_stream_session` 记"这一路的完整过程"，避免每次查询都聚合流水。
- 所有"进行中"记录都有 `status` + `end_reason`，异常断流也能归类（NORMAL / TIMEOUT / SERVER_DOWN / REJECTED）。
- 幂等靠数据库唯一索引 `uk_event_sub(event_id, subscriber_id)`，不依赖 Redis。

## 4. 接口清单

### 4.1 统一返回体

```json
{ "code": 0, "msg": "success", "data": {}, "traceId": "a1b2c3d4" }
```

错误码：`0` 成功 / `1xxx` 参数 / `2xxx` 业务 / `3xxx` 上游(ZLM) / `5xxx` 系统
分页参数：`page`（从1开始）、`size`；返回 `{ total, list }`

### 4.2 对外 REST API（`/api/v1`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/devices` | 设备分页查询 |
| POST/PUT/DELETE | `/devices`、`/devices/{id}` | 设备维护 |
| GET | `/channels` | 通道分页查询（支持 deviceId、status 过滤） |
| POST/PUT/DELETE | `/channels`、`/channels/{id}` | 通道维护 |
| GET | `/streams` | 当前在线流（DB + ZLM 实时合并） |
| GET | `/channels/{id}/play-address` | 签发播放地址（带过期 token，支持 flv/hls/webrtc） |
| POST | `/channels/{id}/record/start`、`/stop` | 录像控制 |
| GET | `/recordings` | 录像台账查询 |
| GET | `/ledger` | **台账查询（核心）**：channelId、eventType、时间范围、分页 |
| GET | `/stats/overview` | 统计看板数据 |
| GET | `/webhook/subscribers` 等 | 订阅者管理 |
| GET | `/webhook/push-logs` | 推送日志 + 手工重推 |
| GET | `/health` | 健康检查（含 ZLM 连通性） |

### 4.3 内部回调接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/hook/zlm/{event}` | ZLM 回调入口，返回 `{"code":0,"msg":"success"}`；非 0 表示拒绝 |

## 5. Webhook 契约

### 5.1 入口（ZLM → 网关）

| ZLM 事件 | 网关处理 |
|---|---|
| `on_publish` | 校验 stream key 是否存在 → 不存在返回 code≠0 拒绝；存在则建流会话、记台账 |
| `on_stream_changed` | regist=true 更新通道在线；false 结束会话、算时长 |
| `on_play` | 校验 token → 记播放会话 |
| `on_stream_none_reader` | 结束播放会话、算观看时长 |
| `on_record_mp4` | 写入录像台账 |
| `on_server_started` | 将所有"进行中"会话标记为异常结束 |

### 5.2 出口（网关 → 下游）

请求头：
```
X-Event-Id:   事件唯一ID（幂等键）
X-Timestamp:  毫秒时间戳
X-Signature:  HMAC-SHA256(secret, timestamp + "." + body) 的十六进制
Content-Type: application/json
```

请求体：
```json
{
  "eventId": "evt_20250101_0001",
  "eventType": "STREAM_DISCONNECTED",
  "occurredAt": "2025-01-01T10:00:00+08:00",
  "deviceCode": "D001",
  "channelCode": "C001",
  "payload": { "streamKey": "live/cam01", "durationSec": 3600 }
}
```

重试策略：10s → 1m → 5m → 30m → 2h，共 5 次；超限标记 `DEAD`，支持手工重推。
下游返回 2xx 视为成功，其余视为失败。
