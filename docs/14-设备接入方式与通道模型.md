## 一、什么样的设备能拉流

### 1.1 先看本质：拉流到底在干什么

拉流 = **我方主动发起一个网络连接，向对方要视频**。所以判定标准不是"有没有 IP"，而是**对方有没有一个能吐流的服务端点**。三个条件缺一不可：

| 条件 | 说明 | 不满足的表现 |
|---|---|---|
| ① 它是**服务端** | 监听某端口，能讲 RTSP / HTTP / RTMP 等协议 | 连不上，或连上没数据 |
| ② 网络**可达** | IP 路由可达 + 端口不被防火墙拦 | `connection timeout` / `refused` |
| ③ **能认证 + 编码兼容** | 有账号密码，且编码我们能解 | `401` / 拉到了但解不出画面 |

### 1.2 UVC 设备"只能推流"这个说法，要纠正一下

严格讲：**UVC 设备（USB 相机、笔记本内置相机）既不能推也不能拉 —— 它自己什么都不做。**

它是 UVC 类设备：插在 USB 上，操作系统把它识别成一个"视频输入设备"（Windows 里就是 DirectShow 设备）。它**没有 IP、没有端口、没有网络协议栈**，只能由本机程序打开它拿原始帧。

所以"推流"这个动作其实是**主机做的**：

```
UVC 只提供原始帧 → 主机上的程序采集 → 编码 → 用 RTMP/RTSP 发出去
                    ↑ 这一步才是"推流"，是 ffmpeg 干的，不是相机干的
```

那能不能让它变成"可被拉流的源"？**能，只要给主机补上"服务端"这一层**：

| 组合 | 结果 |
|---|---|
| USB 相机 + ffmpeg 采集 → 推 RTMP 给 ZLM | 相机变成**推流源**（我们现在的做法） |
| USB 相机 + ffmpeg 采集 → 推 RTSP 给 mediamtx（本机 RTSP 服务器） | mediamtx 对外提供 `rtsp://127.0.0.1:8554/xxx`，**别人就能来拉"这台相机"了** |
| 手机装 RTSP 服务端 App，把摄像头当服务器 | 手机变成一台 IPC（已实测验证） |

**结论**：不是"UVC 只能推"，而是"UVC 本身是传感器，得靠主机给它套一层网络能力"。能不能被拉，取决于**主机上有没有跑服务端**。

### 1.3 "有 IP 就能拉流吗？" —— 不能，这是最常见的误解

有 IP 只满足条件②（可达），不满足①③。反例一大堆：

| 有 IP 但拉不到 | 真正原因 |
|---|---|
| 路由器、打印机、同事的电脑 | 没有流服务，端口上根本没 RTSP |
| 家用摄像头（小米、萤石等） | 默认不开标准 RTSP，走私有协议 + 云 P2P；要在 App 里手动开"局域网 RTSP / ONVIF" |
| 摄像头开了 RTSP 但**只有 H.265** | 能拉到流，但客户端解不了（本项目的 ffmpeg / flv.js 更适合 H.264） |
| 摄像头要求认证 / IP 白名单 / ONVIF 授权 | 401，或干脆不理你 |
| 摄像头在 NAT 后面（从外网访问内网） | 不可达 |

正例：**IPC、NVR/DVR、视频编码器、流媒体服务器（ZLM / mediamtx / SRS）、装了 RTSP 服务端的手机或树莓派**。

一句话：**"能拉流" = 你手里有一个能访问的流 URL + 凭据。**

### 1.4 拉流必须在同一个局域网吗？ —— 不必须，但局域网最简单

| 拓扑 | 例子 | 说明 |
|---|---|---|
| **同机** | `rtsp://127.0.0.1:554/live/fakesrc` | 我们造的假流，最简单 |
| **同局域网** | `rtsp://10.7.25.x:554/...` | 企业里最常见，零配置（前提是 Wi-Fi 没开 AP 隔离） |
| **跨网 / VPN / 专线** | 两边网络打通 | 能拉，需要网络组配合 |
| **公网直连** | 设备开公网 IP 或做端口映射 | 能拉但风险大：RTSP 明文传凭据，公网暴露要配 VPN/白名单 |

这里有一个**非常重要的方向性区别**，能解释很多现实问题：

```
拉流：要求「平台能到设备」 → 设备必须在平台可达的网络里
推流：要求「设备能到平台」 → 设备只要能上网就行（哪怕在 NAT 后面）
```

由此推论：

- 摄像头在**内网 NAT 后面**、平台在云上 → **拉不到**，只能让设备**主动推**（或用 GB28181 注册上来）
- 摄像头和平台在**同一内网** → 拉流最省事
- 平台在云上、摄像头在内网 → 中间架一台**边缘网关**（内网跑 ZLM + 网关，对内拉流，再把转好的流推到云上）

**本项目实测印证**：手机在 `10.7.26.206`（另一段 Wi-Fi）、电脑在 `10.7.25.138` 时，`ping` 通但 **554 端口连不上、服务被 iOS 挂起**；让手机开热点（电脑变 `172.20.10.13`、手机变 `172.20.10.1`）后，`ping 3ms` + `554 可连接` + ffmpeg 解出 `h264 480x640 30fps` —— 本质就是**可达性**问题，不是协议问题。

### 1.5 判断一台设备能不能拉：三步自检

```powershell
# 1. 网络可达
ping 192.168.1.64

# 2. 端口开放（这才是关键，ping 通不代表能拉）
Test-NetConnection 192.168.1.64 -Port 554

# 3. 真正解码测试（这一步才定生死）
ffmpeg -rtsp_transport tcp -i "rtsp://admin:pass@192.168.1.64:554/Streaming/Channels/101" -t 3 -f null -
```

看到 `Stream #0:0: Video: h264 ...` 就是 100% 能拉。

## 二、为什么设计"设备 1 : 通道 N"

### 2.1 先纠正一个常见前提（很关键）

"推流的时候只能同时推到一个通道" —— 这句话**部分对、部分错**：

| 说法 | 对错 | 实际规则 |
|---|---|---|
| 一次推流只能对应**一个**通道 | ✅ 对 | 推流地址里带 `app/stream`，一个 stream 就是一个通道 |
| 一台设备**同时只能推一路** | ❌ 错 | 同一台机器可同时跑多个 ffmpeg，推 N 路到不同 stream id |
| 同一时刻同一个通道只能有**一个发布者** | ✅ 对（真正的限制） | 第二次推同一个流会收到 `Already publishing`（本项目已实测） |

所以真正的约束是"**一个通道同时只能有一个发布者**"，这是防止抢流冲突，**不是限制设备**。

实测：同一台电脑上可以同时推 `live/screencast`（屏幕捕获）和 `live/fakesrc`（彩条），互不影响。

### 2.2 1:N 的四个真实来源

| 来源 | 例子 | 为什么必须 1:N |
|---|---|---|
| **NVR 录像机** | 一台 NVR 后面挂 8/16 台摄像机 | 它是一个"设备"（一个 IP、一份维护合同、一个管理员密码），但对外提供 16 路流。合并成 1:1 就要建 16 个"设备"，资产台账直接失真 |
| **多码流** | 同一台 IPC 同时输出主码流(1080p) + 子码流(720p) | 大屏看主码流、手机看子码流省带宽，两路流的 `streamId` 不同 |
| **一台主机多个视频源** | 我们的电脑：屏幕捕获 `live/screencast` + 假流 `live/fakesrc` | 一台设备 → 两条通道，各自独立推流 |
| **语义分离** | 设备 = 资产（型号/SN/位置/负责人/IP），通道 = 流（app/stream/状态） | 台账要回答"哪台设备、哪路通道、何时、谁看了"，两层拆开才能都答 |

### 2.3 那 1:1 行不行？技术上完全可以

把每路流都建成一台"设备"（NVR 的 16 路 → 16 台设备），系统照样能跑。但有四个代价：

| 代价 | 具体后果 |
|---|---|
| **资产台账失真** | 一台 NVR 变成 16 条设备记录；设备数、厂商、IP、维护记录全冗余 16 份，"我们有多少台设备"直接算错 |
| **状态派生失效** | 现在的规则是"设备在线 = 它任一通道非离线"，符合直觉。拆成 1:1 后，一台机器在线会被算成 16 台设备各自在线 |
| **扩展性差** | 将来加"固件版本 / 采购日期 / 保修 / 责任人 / 地理位置"这些**设备级**字段，全要冗余 16 次，改一次错 16 处 |
| **对接行业标准要转换** | GB28181、ONVIF、WVP-PRO 全是 `device → channel` 两级模型；1:1 建模要额外写映射层 |

### 2.4 什么时候 1:1 就够

如果业务永远是"一台单路 IPC + 一个流"，1:1 确实更简单：少一张表、少一层关联。

但本项目的定位是**接各种设备、每台可能多路、还要对多个业务方做通道级隔离** —— 这种场景下 **1:N 是最小必要冗余**：多一张表、一个 `device_id` 外键，换来"资产"和"流"各管各的。

### 2.5 一个诚实的现状（我们库里正好有反例）

现在库里的测试通道（`CH-PULL-DST`、`CH-FAKE-SRC`、`CH-MY-*` 等）**几乎全挂在 `DEV-USB-001 USB摄像头-01` 这台设备下** —— 因为建测试通道时图省事都挂同一个设备。

这是典型的"把设备当挂靠点用"，概念上不严谨：

- 严格建模的话，`CH-FAKE-SRC`（彩条假流）不该属于"USB摄像头"这台设备
- 更合理的是建一台 `DEV-VIRTUAL-001 虚拟流源`，把假流、拉流测试通道挂过去

不影响功能（设备状态派生只是"任一通道非离线"），但答辩被问"为什么彩条流挂在 USB 摄像头下"会尴尬。属于数据整理，需要时再做。

## 三、速查表

| 问题 | 答案 |
|---|---|
| UVC 能拉流吗 | 不能，它没有网络能力，只能被本机程序采集后**由主机推**出去 |
| 有 IP 就能拉流吗 | 不能。要"服务端在监听 + 可达 + 能认证/编码兼容"三件事 |
| 拉流必须同局域网吗 | 不必须，但最省事；跨网需要 VPN/专线/端口映射，且 RTSP 明文有安全风险 |
| 为什么 NAT 后的设备拉不到 | 拉流要求"平台能到设备"；NAT 后设备只能反过来**推**，或用 GB28181 注册 |
| 一次推流能推几个通道 | 一次推流（一个 `app/stream`）对应一个通道；同一通道同时只能有一个发布者 |
| 一台设备能同时推几路 | 想推几路推几路，只要 `streamId` 不同 |
| 设备:通道 一定要 1:N 吗 | 不一定，但资产/流语义分离 + NVR 多路 + 行业标准，使 1:N 成为最小必要冗余 |
| 怎么快速判断某设备能拉 | `ping` → `Test-NetConnection -Port 554` → `ffmpeg -i <rtsp地址> -t 3 -f null -` |

## 四、术语小抄

| 名词 | 一句话 |
|---|---|
| **UVC** | USB Video Class，USB 摄像头标准，本机设备，无网络能力 |
| **DirectShow** | Windows 的多媒体采集框架，ffmpeg 用 `-f dshow` 打开本地摄像头 |
| **RTSP** | 实时流协议，安防摄像头最通用出口，默认 554 端口，浏览器不能直接播 |
| **ONVIF** | 网络摄像头的统一互通标准（设备发现 + 取流地址），开 RTSP 不一定开 ONVIF |
| **GB28181** | 国标：设备**主动注册**到上级平台并推流，是"推"不是"拉" |
| **NAT** | 网络地址转换，内网设备对外不可见，导致外部拉不进来 |
| **AP 隔离** | Wi-Fi 的客户端隔离，同一 Wi-Fi 的设备之间也互相访问不了（公司 Wi-Fi 常见） |
| **NVR / DVR** | 网络录像机 / 数字录像机，一台设备对外提供多路通道（1:N 的典型来源） |
