# 接口使用手册（33 个接口逐个说明）

> 面向两类读者：
> 1. **联调/测试**（Apifox、Postman、curl）—— 想知道每个接口填什么、返回什么；
> 2. **业务方对接** —— 想知道"我要看某路视频"该调哪几个。

---

## 0. 通用约定（先看这一段，后面所有接口都适用）

### 0.1 Base URL

```
http://127.0.0.1:8088
```

### 0.2 鉴权

所有 `/api/v1/**` 接口（除 `/api/v1/health`）都要带请求头：

```
api-key: vwg_console
```

值就是「API 客户端」里发放的 **appKey**（不是 appSecret）。缺头/无效/停用/过期都会返回 HTTP 401 + `code=1001`。

### 0.3 统一返回体

```json
{ "code": 0, "msg": "success", "data": { ... }, "traceId": "ecf14011f55a434e", "success": true }
```

| 字段 | 说明 |
|---|---|
| `code` | 0 成功，其它见下表 |
| `msg` | 人话描述（失败时前端可直接展示） |
| `data` | 业务数据；失败时**不出现**（非 null） |
| `traceId` | 本次请求链路号，排查时拿它去日志里搜 |
| `success` | `code == 0` 的布尔版，方便前端判断 |

| code | 含义 | 典型场景 |
|---|---|---|
| 0 | 成功 | |
| 1000 | 参数错误 | 必填项为空、地址协议不支持 |
| 1001 | 未授权 | 缺 key / 无效 / 已停用 / 已过期 / 无权访问该通道 |
| 2001 | 资源不存在 | 通道 id 不存在 |
| 2002 | 资源已存在 | 设备编码/通道编码/流标识重复 |
| 2003 | 当前状态不允许该操作 | 重复发起拉流、停一个没有的拉流任务、给控制台配隔离 |
| 3001 | 媒体服务器调用失败 | 拉流地址连不上、流不在线没法录像 |
| 3002 | 媒体服务器不可达 | ZLM 没启动 |
| 5000 | 系统内部错误 | 兜底 |

### 0.4 分页

列表接口统一用 query 参数 `page`（默认 1）、`size`（默认 10，**最大 200**），返回：

```json
{ "total": 275, "page": 1, "size": 10, "list": [ ... ] }
```

### 0.5 通道级隔离

每个 api-key 可以配"只能访问哪些通道"（`allowed_channels`）。配置后，**列表接口只返回授权通道的数据，针对未授权通道的动作直接 1001 并记台账**。未配置 = 不限（管理控制台就是这样）。

设备列表与总览统计**不隔离**（设备是登记信息、统计是运营视角），这是有意设计。

### 0.6 时间与空值

- 时间格式统一 `yyyy-MM-dd HH:mm:ss`（入参也接受 `2026-11-02T09:40:00`、带毫秒、只传日期）
- 值为空的字段**不会出现在响应里**（不是 `null`）

### 0.7 状态枚举

| 对象 | 字段 | 取值 |
|---|---|---|
| 设备/通道 | `enabled` | 1 启用 / 0 停用 |
| 设备 | `status` | 1 在线 / 0 离线（**派生值**：该设备下任一通道非离线 = 在线） |
| 通道 | `status` | 2 有流在跑 / 1 在线（预留）/ 0 离线（**界面统一显示"在线/离线"两态**） |
| 流会话 | `status` | 1 进行中 / 2 正常结束 / 3 异常结束 |
| 录像 | `status` | 2 已完成（目前只有这一种） |
| 录像 | `fileExists` | 1 文件在磁盘 / 0 已被清理（记录保留） |

### 0.8 台账事件类型（`eventType`）

| 分组 | 事件 |
|---|---|
| 推流 | `PUBLISH_START` / `PUBLISH_STOP` / `PUBLISH_REJECT` |
| 拉流 | `STREAM_PULL_START` / `STREAM_PULL_STOP`（命令下发） |
| 播放 | `PLAY_START` / `PLAY_STOP` |
| 录像 | `RECORD_START` / `RECORD_STOP` / `RECORD_FINISH` / `RECORD_PURGED` |
| 接口 | `API_CALL`（含越权被拒，`resultCode=2003`） |
| 授权 | `AUTH_CHANGED`（通道/设备删除后自动从客户端授权中移除） |
| 设备/系统 | `DEVICE_ONLINE` / `DEVICE_OFFLINE` / `SERVER_STARTED` / `STATE_RECONCILE` |

`source` 取值：`ZLM`（媒体服务器回调）/ `API`（第三方调用）/ `MANUAL`（控制台人工操作）/ `TIMER`（定时对账）。

## 1. 健康检查（1 个）

### 1.1 `GET /api/v1/health` 服务健康检查

**用途**：探活。同时检查数据库连接和媒体服务器是否可用，部署后第一个要调的接口。
**鉴权**：**不需要 api-key**（唯一豁免的业务接口）。
**参数**：无。

```json
{ "code":0, "data": { "database": true, "zlm": true, "status": "UP" } }
```

**怎么用**：K8s/监控探针、启动脚本自检。`zlm=false` 说明 ZLM 没起或 secret 不对。

## 2. 统计看板（1 个）

### 2.1 `GET /api/v1/stats/overview` 总览统计

**用途**：首页四个卡片的数据源。全部从台账和会话表算出来，不额外维护计数器。
**参数**：无。
**返回**：

```json
{ "channelTotal":11, "channelOnline":1, "runningSessions":1,
  "todayPublishCount":10, "todayPlayCount":28, "todayRejectCount":0,
  "ledgerTotal":275, "zlmAvailable":true }
```

**注意**：这是**全局口径**，不做通道隔离（控制台/运营视角）。

## 3. 设备管理（5 个）

设备 = 物理设备台账（一台 IPC、一个 NVR、一台手机）。一台设备可以有多个通道（主码流/子码流）。

### 3.1 `GET /api/v1/devices` 分页查询设备

| 参数 | 必填 | 说明 |
|---|---|---|
| `page` / `size` | 否 | 分页，默认 1 / 10 |
| `keyword` | 否 | 按**设备名称**模糊搜 |
| `status` | 否 | 1 在线 / 0 离线 |

```bash
GET /api/v1/devices?page=1&size=50
```

### 3.2 `GET /api/v1/devices/{id}` 查询单个设备

**用途**：详情页、或者查完列表拿 id 核对。不存在返回 `2001 设备不存在`。

### 3.3 `POST /api/v1/devices` 新增设备

**Body**（`deviceCode`、`deviceName` 必填）：

```json
{
  "deviceCode": "DEV-CAM-003",
  "deviceName": "三楼走廊摄像机",
  "deviceType": "IPC",
  "manufacturer": "海康",
  "ipAddress": "192.168.1.64",
  "enabled": 1,
  "remark": "走廊东侧"
}
```

- 返回新建对象（含 `id`，后续建通道要用）
- 编码重复 → `2002 设备编码已存在`
- 若该编码曾被逻辑删除，会**自动复用**那条记录（保住历史台账引用）

### 3.4 `PUT /api/v1/devices/{id}` 修改设备

**Body**：同新增（`deviceCode` 不可改，其余可改）。返回修改后的对象。

### 3.5 `DELETE /api/v1/devices/{id}` 删除设备

**逻辑删除**：数据行保留（`deleted=1`），历史台账依旧能按 id 追溯。
**注意**：
- 删除设备**不会**自动删它下面的通道，建议先处理通道；
- 但会自动把该设备从各客户端的"设备级授权"（`allowed_devices`）里摘掉，并记一条 `AUTH_CHANGED` 台账。

## 4. 通道管理（6 个）

通道 = 一路可播放的流。`streamApp/streamId`（合称**流标识**，如 `live/usbcam`）是它和媒体服务器之间的唯一纽带。

### 4.1 `GET /api/v1/channels` 分页查询通道

| 参数 | 必填 | 说明 |
|---|---|---|
| `page` / `size` | 否 | 分页 |
| `deviceId` | 否 | 只看某台设备的通道 |
| `status` | 否 | 0/1/2 |
| `keyword` | 否 | 按**通道名称**模糊搜 |

**返回**每行包含 `deviceName`（所属设备名称，批量补齐，不用再查设备表）。
**隔离**：受限客户端只看到授权通道。

### 4.2 `GET /api/v1/channels/{id}` 查询单个通道

同上，单条。带 `deviceName`。越权返回 `1001 该客户端无权访问通道 xxx`。

### 4.3 `POST /api/v1/channels` 新增通道

**Body**（`deviceId`、`channelCode`、`channelName`、`streamApp`、`streamId` 必填）：

```json
{
  "deviceId": 6,
  "channelCode": "CH-CAM-003-01",
  "channelName": "三楼走廊-主码流",
  "streamApp": "live",
  "streamId": "cam03",
  "pullUrl": "",
  "enabled": 1
}
```

**三种接入方式怎么填**：

| 接入方式 | 怎么填 |
|---|---|
| 设备推流（USB 摄像头、编码器、手机） | `pullUrl` 留空。让设备推 `rtmp://127.0.0.1/live/cam03` |
| 平台拉流（网络摄像头 IPC、NVR） | 填 `pullUrl`，如 `rtsp://admin:pass@192.168.1.64:554/Streaming/Channels/101`，然后调 `POST /channels/{id}/pull` |
| GB28181 | 本期未做（预留 openRtpServer） |

- 流标识重复 → `2002 流标识已被占用: live/cam03`
- 通道编码重复 → `2002 通道编码已存在`

### 4.4 `PUT /api/v1/channels/{id}` 修改通道

**Body**：同新增。**注意**：`channelCode`、`streamApp`、`streamId` **不参与修改**（流标识是台账快照的锚点，不允许改），可改的是 `deviceId`、`channelName`、`pullUrl`、`enabled`。

### 4.5 `DELETE /api/v1/channels/{id}` 删除通道（并从各客户端授权中自动移除）

逻辑删除。流标识仍被占用，再次登记同一流标识会自动复用这条记录。

删除时会自动把该通道从所有客户端的 `allowed_channels` 里摘掉，并记一条 `AUTH_CHANGED` 台账——
避免授权里留下指向"已删除通道"的脏引用（界面上会显示"通道 #9：已删除或不存在"）。

### 4.6 `GET /api/v1/channels/{id}/probe` 探测流标识真实状态

**用途**：排查"通道显示离线，但设备明明在推"这类问题。直接问媒体服务器：这路流在不在、是推还是拉、有多少人看、有没有残留的拉流任务。

```json
{
  "channelId":18, "channelCode":"CH-PULL-DST", "streamKey":"live/pull1",
  "online":true, "originType":4, "originName":"拉流",
  "schemas":"fmp4, hls, rtmp, rtsp, ts", "readerCount":0, "recording":false,
  "proxyRegistered":true, "proxyKey":"__defaultVhost__/live/pull1",
  "pullUrl":"rtsp://127.0.0.1:554/live/src1",
  "pushUrl":"rtmp://127.0.0.1/live/pull1",
  "rtspUrl":"rtsp://127.0.0.1:554/live/pull1",
  "httpFlvUrl":"http://127.0.0.1/live/pull1.live.flv",
  "conclusion":"拉流任务正常：流已上线（观看 0 人），可以正常取播放地址"
}
```

**`conclusion` 会直接告诉你该怎么办**，例如：
- "流标识当前不存在：该通道是拉流型，可以直接【发起拉流】"
- "拉流任务已注册但流还没上线：多半是拉流地址不通或设备未就绪，可点【停止拉流】清理残留代理后重试"

## 5. 流与播放（4 个）—— **业务平台最常用的就是这一组**

### 5.1 `GET /api/v1/streams` 查询在线流

**用途**：业务平台"我有哪些流可以看"。把数据库里的通道和媒体服务器的实时状态合在一起。
**参数**：无。

```json
{ "channelId":3, "channelCode":"CH-USB-001", "channelName":"USB摄像头-01-主码流",
  "streamKey":"live/usbcam", "status":2, "online":true, "readerCount":1,
  "schemas":["rtmp","rtsp","ts","hls","fmp4"], "recording":false,
  "originType":1, "pulled":false, "originName":"推流" }
```

| 字段 | 说明 |
|---|---|
| `online` | 媒体服务器上是否有这路流的源 |
| `originType` / `originName` / `pulled` | 1/2 推流、3/4/5/7 拉流 |
| `readerCount` | 当前观看人数（ZLM 分发，一个人看五个协议也只算一路的下游） |

### 5.2 `GET /api/v1/channels/{id}/play-address` 签发播放地址

**调用链里最核心的一个**：业务平台拿它把"通道 id"换成可直接播放的 URL。

| 参数 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 路径参数，通道 id |
| `protocol` | 否 | `flv`（默认）/ `ws-flv` / `hls` / `webrtc` / `rtsp` / `rtmp` |

```bash
GET /api/v1/channels/3/play-address?protocol=flv
```

```json
{ "channelId":3, "channelName":"USB摄像头-01-主码流", "streamKey":"live/usbcam",
  "protocol":"flv", "url":"http://127.0.0.1/live/usbcam.live.flv",
  "online":true, "lowLatency":true }
```

**协议怎么选**：

| 协议 | URL | 延迟 | 场景 |
|---|---|---|---|
| `flv` | `http://host/live/usbcam.live.flv` | 1~3 秒 | **Web 首选**（flv.js），兼容好 |
| `ws-flv` | `ws://host/...live.flv` | 1~3 秒 | 需要走 WebSocket 的网络环境 |
| `hls` | `http://host/live/usbcam/hls.m3u8` | 10~30 秒 | 手机原生播放器、CDN 分发 |
| `webrtc` | `http://host/index/api/webrtc?app=..&stream=..&type=play` | < 500ms | 对讲/低延迟 |
| `rtsp` | `rtsp://host:554/live/usbcam` | 1~2 秒 | 后端/嵌入式拉流 |
| `rtmp` | `rtmp://host/live/usbcam` | 1~2 秒 | OBS 等推拉流工具 |

**注意**：`online=false` 时地址也给（通道登记了就能拿到），但此时播放会失败 —— 先看 `online`。
**越权**：受限客户端请求未授权通道 → `1001`，并记一笔台账（`resultCode=2003`）。

### 5.3 `POST /api/v1/channels/{id}/pull` 平台发起拉流

**用途**：把一台**只提供 RTSP、不会主动连我们**的网络摄像头接进来。网关调媒体服务器的拉流代理去拉，拉到的流注册成 `app/stream`，之后和推流完全一样（一套地址、五个协议）。
**前置条件**：通道已填 `pullUrl`、已启用、当前没有流。
**参数**：无 body。

```json
{ "channelId":18, "streamKey":"live/pull1", "pullUrl":"rtsp://127.0.0.1:554/live/src1",
  "proxyKey":"__defaultVhost__/live/pull1", "pulling":true,
  "tip":"拉流任务已下发。若 3~5 秒内通道仍未变「在线」，说明拉流地址连不上，可点【探测】查看..." }
```

**注意**：
- 命令下发 ≠ 流已上线，中间有 1~3 秒；用 `probe` 或 `status` 确认
- 源不通时返回 `3001 拉流失败：连不上拉流地址（play rtsp timeout）...`，且不会留残留任务
- 源协议不支持时返回 `3001 拉流失败：媒体服务器不支持这种源协议（not supported play schema:...）...`
- 其它拒绝统一返回 `3001 拉流失败：媒体服务器拒绝了这次拉流`，ZLM 原始报文只写日志
- 台账会记两条：`STREAM_PULL_START`（命令）+ `PUBLISH_START`（流真的上线了）

### 5.4 `POST /api/v1/channels/{id}/unpull` 停止拉流

删除拉流代理，流随之注销（通道回离线、会话结算）。没有任务可停时返回 `2003 该通道当前没有进行中的拉流任务，无需停止`。

## 6. 录像管理（5 个）

设计取舍：**关闭 ZLM 全局自动录像**（否则 900MB/小时写满盘），改为**按需开启**。

### 6.1 `POST /api/v1/channels/{id}/record/start` 开始录像

**参数**：无 body。**前提**：该路流必须在线，否则 `3001 开始录像失败: can not find the stream`。
录制按 ZLM 配置切片（本项目 `fileSecond=60`），每个切片完成时媒体服务器回调，自动写入录像台账。

### 6.2 `POST /api/v1/channels/{id}/record/stop` 停止录像

停止后当前切片会落盘并写台账（`RECORD_FINISH`）。

### 6.3 `GET /api/v1/recordings` 分页查询录像台账

| 参数 | 说明 |
|---|---|
| `page` / `size` | 分页 |
| `channelId` | 只看某通道 |

```json
{ "id":6, "channelId":3, "streamKey":"live/usbcam", "fileName":"09-15-38-0.mp4",
  "filePath":"http://127.0.0.1/record/live/usbcam/2026-11-02/09-15-38-0.mp4",
  "fileSize":1989631, "durationSec":1,
  "videoStartTime":"2026-11-02 09:15:38", "videoEndTime":"2026-11-02 09:15:39",
  "source":"AUTO", "status":2, "fileExists":1 }
```

`filePath` 是**可直接播放的 HTTP 地址**（ZLM 的 www 目录对外发布）。

### 6.4 `POST /api/v1/recordings/{id}/purge` 清理录像文件

**只删磁盘文件、保留台账记录**（`fileExists` 置 0、记 `purgedTime`），并返回释放了多少空间。审计账不该被抹掉，磁盘空间也必须能回收 —— 两者兼顾。

```json
{ "releasedBytes":20736000, "releasedMb":19.8, "diskDeleted":true,
  "message":"清理录像文件，释放 19.8 MB（台账记录保留）" }
```

### 6.5 `GET /api/v1/recordings/{id}/download` 下载录像文件

**返回二进制 mp4**（不是 JSON），响应头带 `Content-Disposition: attachment`，浏览器点开就是另存为。

```text
HTTP/1.1 200
Content-Type: video/mp4
Content-Disposition: attachment; filename*=UTF-8''usbcam_09-15-38-0.mp4
Content-Length: 1989631
Accept-Ranges: bytes
```

**为什么不直接把 `filePath` 丢给浏览器**：那样是直连 ZLM 的静态目录，会绕过 `api-key` 鉴权与通道级隔离，
也查不到"谁下载了哪段录像"。走这个接口则：鉴权 + 隔离 + 记台账（`API_CALL 下载录像文件 xxx`）一条不落。

**注意**：

- 文件名规则：`{流标识}_{原文件名}`，例如 `usbcam_09-15-38-0.mp4`（原文件名只有时间，多路通道会重名）
- 流式返回，几十 MB 到 GB 都不会把内存打满；支持 `Range`，浏览器可断点续传
- 文件已被清理（`fileExists=0`）→ `2003 这段录像的文件已经清理过了，无法下载`
- 磁盘文件被手工删掉 → `2001 录像文件在磁盘上找不到了（可能被手工删除），台账记录仍然保留`

命令行下载：

```bash
curl -H "api-key: vwg_console" -OJ http://127.0.0.1:8088/api/v1/recordings/6/download
```

## 7. 台账与流会话（2 个）

### 7.1 `GET /api/v1/ledger` 分页查询业务台账

**这是"写台账"这个需求的查询面**。所有业务动作都在这里留痕。

| 参数 | 说明 |
|---|---|
| `page` / `size` | 分页 |
| `channelId` / `deviceId` | 按通道/设备过滤 |
| `clientId` | 按调用方（api-key）过滤 |
| `eventType` | 单个事件类型，如 `PLAY_START` |
| `eventTypes` | **多个**，逗号分隔，如 `PUBLISH_START,PUBLISH_STOP` |
| `beginTime` / `endTime` | 时间范围 `yyyy-MM-dd HH:mm:ss` |

```json
{ "id":275, "bizNo":"LG202611021521245011", "eventType":"API_CALL",
  "eventTime":"2026-11-02 15:21:24", "deviceId":1, "channelId":1,
  "channelCode":"CH-CAM-001", "streamKey":"live/cam01", "clientId":13,
  "source":"API", "resultCode":2003, "resultMsg":"该客户端无权访问通道 CH-CAM-001" }
```

**两个设计点**：
- `channelCode` / `streamKey` 是**事发当时的快照**，通道改名/删除后历史台账不失真
- 每次越权尝试都会留一条 `resultCode=2003` 的记录 —— 审计时"被拒绝的访问"比"成功的访问"更有价值

### 7.2 `GET /api/v1/sessions` 分页查询流会话

**用途**：一次推流/拉流 = 一条会话，带时长和结束原因。适合做"这个月设备在线多久"这类统计。
**与台账的区别**：会话是**聚合视图**（一次流一行），台账是**流水视图**（一个事件一行）。

| 参数 | 说明 |
|---|---|
| `channelId` / `status` | 过滤（1 进行中 / 2 正常结束 / 3 异常结束） |
| `beginTime` / `endTime` | 按开始时间过滤 |

```json
{ "sessionNo":"SS202611021455489920", "channelId":3, "streamKey":"live/usbcam",
  "clientIp":"127.0.0.1", "trackCount":1, "startTime":"2026-11-02 14:55:49",
  "endTime":"2026-11-02 15:21:10", "durationSec":1521, "endReason":"NORMAL", "status":2 }
```

`endReason`：`NORMAL` 正常断流、`TIMEOUT` 对账超时、`SERVER_DOWN` 媒体服务器重启。

## 8. API 客户端管理（8 个）

给业务平台发放凭证。**这组接口自己也要 api-key**（用管理控制台的 key 来调）。

### 8.1 `POST /api/v1/api-clients` 创建客户端

```json
{ "clientName":"A系统-测试平台", "contact":"李宁(工号1024)",
  "remark":"门禁对接", "expireTime":"2027-12-31 23:59:59",
  "allowedChannels":[3, 9] }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `clientName` | 是 | 客户端名称 |
| `contact` | 否 | 联系人（出问题找谁） |
| `expireTime` | 否 | 不填 = 长期有效；格式 `yyyy-MM-dd HH:mm:ss` |
| `allowedChannels` | 否 | 单通道授权；不填/空数组 = 该维度不限 |
| `allowedDevices` | 否 | **设备级授权**：该设备名下所有通道（含以后新增）都算授权 |
| `scopeMode` | 否 | `ALL`=全部通道（不传时的默认值）；`SCOPE`=按上面两个列表授权，两个都空则**全拒**。
 本项目前端创建时固定传 `SCOPE`+空列表 = 默认无授权，需再调 `/api-clients/{id}/channels` 分配 |
| `isAdmin` | 否 | **管理权限（超管）**：1=可调用全部接口（客户端管理/统计/设备增删改）；默认 0。
 与通道范围无关：`ALL` 通道 ≠ 有管理权限 |

返回**只此一次**的 `appSecret`：

```json
{ "id":14, "appKey":"vwg_XXXXXXXXXXXX", "appSecret":"32位随机串",
  "clientName":"...", "tip":"appSecret 仅此一次可见，请立即保存" }
```

> `appKey` 用于接口鉴权；`appSecret` 目前只用于下一步的播放地址签名，**不参与接口鉴权**。

### 8.2 `GET /api/v1/api-clients` 分页查询客户端

`page` / `size`。**不返回 appSecret**（只回 `******`）。含 `allowedChannels`（逗号分隔的通道 id 或 null）。

### 8.3 `POST /api/v1/api-clients/{id}/channels` 配置授权范围（通道 + 管理权限）

```json
{ "allowedChannels": [3, 9] }
```

- 传 `[]` = 改为**不限**
- 通道不存在 → `1000 通道不存在: [999]`
- **控制台客户端 `vwg_console` 不允许配置**（否则界面会把自己锁死）→ `2003`

### 8.4 `POST /api/v1/api-clients/{id}/expire` 修改失效时间（续期）

```json
{ "expireTime": "2027-12-31 23:59:59" }
```

传 `null` = 改为永久有效；传过去的时间 = 立即失效（做演示很好用）。
之所以单独开这个接口：以前只能"删了重建"，配错一次就得换 appKey。

### 8.5 `POST /api/v1/api-clients/{id}/reset` 重置密钥

返回新的 `appSecret`（旧密钥立即失效）。**appKey 不变**，所以业务方不用改代码里的 key。

### 8.6 `POST /api/v1/api-clients/{id}/enable` 启用

### 8.7 `POST /api/v1/api-clients/{id}/disable` 停用

停用后该 key 的请求**立即**被拒（`1001 该客户端已被停用`），无需等过期。

### 8.8 `DELETE /api/v1/api-clients/{id}` 删除

逻辑删除。已经用这个 key 记过的台账仍然保留 `clientId`。

## 9. 媒体服务器回调（1 个，**内部接口**）

### 9.1 `POST /hook/zlm/{event}`

**用途**：给 ZLMediaKit 回调用的，**业务方不要调**。鉴权豁免（ZLM 不带 api-key）。

支持的事件：`on_publish`（推流鉴权，返回非 0 即拒绝推流）、`on_stream_changed`、`on_play`、`on_stream_none_reader`、`on_record_mp4`、`on_server_started`。

**为什么它是"网关"而不是"转发器"的关键**：ZLM 只会告诉你"有人推流了 / 断流了"，是我们在这里把它翻译成**台账、会话、设备状态**。

## 10. 推荐上手顺序（联调时照这个走）

| 步骤 | 调什么 | 期望 |
|---|---|---|
| 1 | `GET /health` | `status=UP`，`zlm=true`（ZLM 没起就先起它） |
| 2 | `GET /devices` → `POST /devices` | 建一台测试设备，记下 `id` |
| 3 | `POST /channels` | 建一路通道，`streamId` 记成 `apifoxtest` |
| 4 | 用 ffmpeg 推 `rtmp://127.0.0.1/live/apifoxtest` | 通道 status 变 2，台账出现 `PUBLISH_START` |
| 5 | `GET /channels/{id}/probe` | `online=true`、`originName=推流` |
| 6 | `GET /channels/{id}/play-address?protocol=flv` | 拿到 flv 地址，用 flv.js/浏览器插件能播 |
| 7 | `GET /streams`、`GET /sessions`、`GET /ledger` | 能看到上面这一连串动作的痕迹 |
| 8 | `POST /channels/{id}/record/start` → 等 60 秒 → `/stop` | `GET /recordings` 出现录像 |
| 8b | `GET /recordings/{id}/download` | 浏览器另存为 mp4，台账出现 `下载录像文件 xxx` |
| 9 | `POST /api-clients` | 建一个受限客户端（`allowedChannels:[3]`） |
| 10 | 用受限 key 调 `GET /channels` | 只返回 1 条；调别的通道 → `1001` + 台账留痕 |
| 11 | `POST /channels/{id}/pull`（拉流通道） | `live/pullX` 上线，`originType=4` |

## 11. 五个最容易踩的坑

1. **`api-key` 填 appKey，不是 appSecret**
2. `api-key` 缺/错/停用/过期 → **HTTP 401**，body 里仍是统一返回体（`code=1001`）
3. 通道 `streamApp/streamId` 建好后**不能改**（要改就新建一条通道）
4. 拉流/录像都要求**流在线**，`3001` 先去看 `probe`
5. 时间参数一律 `yyyy-MM-dd HH:mm:ss`，别写 ISO 的 `T`（虽然也兼容，但统一更好维护）
