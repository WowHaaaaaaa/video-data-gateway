## 三、逐表说明

### 3.1 `biz_device` 视频设备

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | 自增主键 |
| `device_code` | VARCHAR(64) **UNIQUE** | 业务唯一编号，对外契约 |
| `device_name` | VARCHAR(128) | 设备名称 |
| `device_type` | VARCHAR(32) | 接入类型：RTMP / RTSP / GB28181 |
| `manufacturer` / `ip_address` | | 现场对接信息 |
| `status` | TINYINT | **运行态**：0 离线 / 1 在线 |
| `enabled` | TINYINT | **配置态**：0 停用 / 1 启用 |
| `deleted` | TINYINT | 逻辑删除 |

> **`status` 与 `enabled` 必须分开**：前者是系统自动维护的"现在怎么样"，
> 后者是人工控制的"允不允许"。一台设备可以"启用但离线"，也可能被"停用但流还在跑"。

### 3.2 `biz_channel` 视频通道 ★

| 字段 | 说明 |
|---|---|
| `device_id` | 所属设备（1 设备 N 通道：主码流/子码流/NVR 下挂多路） |
| `channel_code` | 通道业务编码（唯一） |
| `stream_app` | ZLM 的应用名，如 `live` |
| `stream_id` | **ZLM 的流 ID，推流鉴权的核心契约** |
| `pull_url` | 源拉流地址（拉流型设备才填） |
| `status` | 0 离线 / 1 在线 / 2 有流在跑（前端统一显示"在线/离线"两态） |
| `last_online_time` | 最近一次上线时间 |

**索引**：
```sql
UNIQUE KEY uk_stream_key (stream_app, stream_id)   -- 流标识不能被两个通道抢
UNIQUE KEY uk_channel_code (channel_code)
KEY idx_device_id (device_id)
```

> ⭐ `uk_stream_key(stream_app, stream_id)` 就是**联合唯一键**的典型用法：
> 单独 `stream_app=live` 可以重复无数次，单独 `stream_id=cam01` 也可以重复，
> 但 `(live, cam01)` 这个组合全库只能有一个。

### 3.3 `biz_stream_session` 流会话（聚合台账）★

| 字段 | 说明 |
|---|---|
| `session_no` | 会话单号 `SS + 时间戳 + 随机4位`（唯一） |
| `channel_id` | 哪一路通道 |
| `stream_key` | `app/stream`（便于直接按流查） |
| `client_ip` | 推流方 IP |
| `track_count` | 媒体轨道数（视频+音频） |
| `start_time` / `end_time` | 起止时间 |
| `duration_sec` | **持续秒数（自动计算，核心统计字段）** |
| `end_reason` | NORMAL / TIMEOUT / SERVER_DOWN / REJECTED |
| `status` | 1 进行中 / 2 正常结束 / 3 异常结束 |

**作用**：回答"这路流播了多久、怎么结束的"，一次查询出结果，不需要聚合流水。

### 3.4 `biz_ledger` 业务台账（事件流水）★核心

| 字段 | 说明 |
|---|---|
| `biz_no` | 业务流水号 `LG + 时间戳 + 随机4位`（唯一） |
| `event_type` | 事件类型（见下表） |
| `event_time` | `DATETIME(3)` 毫秒精度 |
| `device_id` / `channel_id` | 归属（可为空：未注册的推流就没有归属） |
| `ref_id` | 关联的会话/播放/录像 ID |
| **`client_id`** | **调用方客户端（新增）；NULL 表示内部事件** |
| `source` | 来源：ZLM / API / TIMER / MANUAL |
| `client_ip` / `operator` | 谁 |
| `result_code` | 0 成功，其他为错误码 |
| `detail` | **JSON：原始报文，便于追溯与二次解析** |

**事件类型枚举**

| 类型 | 触发 | 归属 |
|---|---|---|
| `PUBLISH_START` | 推流开始 | ZLM 回调 |
| `PUBLISH_STOP` | 推流结束 | ZLM 回调 |
| `PUBLISH_REJECT` | 推流被拒 | ZLM 回调 |
| `PLAY_START` / `PLAY_STOP` | 播放开始/结束 | ZLM 回调 |
| `RECORD_START` / `RECORD_STOP` | 手工录像开关 | API |
| `RECORD_FINISH` | 录像文件生成 | ZLM 回调 |
| `SERVER_STARTED` | 媒体服务器启动 | ZLM 回调 |
| `DEVICE_ONLINE` / `DEVICE_OFFLINE` | 设备上下线 | 预留 |

**索引**
```sql
UNIQUE KEY uk_biz_no (biz_no)
KEY idx_event_time (event_time)                    -- 按时间范围查
KEY idx_channel_time (channel_id, event_time)      -- 某通道的历史（最常用）
KEY idx_type_time (event_type, event_time)         -- 按事件类型统计
KEY idx_client_time (client_id, event_time)        -- 某客户端的行为（新增）
```

### 3.5 `biz_play_session` 播放会话（预留）

**当前代码未接入**，暂时用 `biz_ledger` 的 PLAY_START/PLAY_STOP 覆盖。

### 3.6 `biz_recording` 录像台账

| 字段 | 说明 |
|---|---|
| `file_path` | **存可直接回放的 http URL**（不是本地路径） |
| `file_size` / `duration_sec` | 文件大小、时长 |
| `video_start_time` / `video_end_time` | 视频内容时间段 |
| `source` | MANUAL（手工 API）/ AUTO（自动） |
| `status` | 1 录制中 / 2 已完成 / 3 异常 |

> ⚠️ **踩坑记录**：ZLM 在 Windows 下按 GBK 输出回调 JSON，`file_path` 里的中文目录会变乱码

### 3.7 `biz_webhook_subscriber` 订阅者

| 字段 | 说明 |
|---|---|

| `secret` | HMAC 签名密钥 |
| `event_types` | 订阅的事件类型，逗号分隔，`*` 表示全部 |
| `enabled` | 启停 |

### 3.8 `biz_webhook_push_log` 推送日志（兼重试队列）★

| 字段 | 说明 |
|---|---|
| `event_id` | 事件唯一 ID（幂等键） |
| `subscriber_id` | 推给哪个下游 |
| `payload` | 推送报文（JSON） |
| `attempt` | 已尝试次数 |
| `next_retry_time` | 下次重试时间 |
| `status` | 0 待推送 / 1 成功 / 2 失败待重试 / 3 死亡 |

```sql
UNIQUE KEY uk_event_subscriber (event_id, subscriber_id)   -- 幂等
KEY idx_status_retry (status, next_retry_time)             -- 扫描待重试
```

重试策略：`10s → 1m → 5m → 30m → 2h`，共 5 次；超限置 `3 死亡`，支持手工重推。

## 四、索引命名规范（`uk_` 到底是啥）

### 4.1 命名约定

```sql
UNIQUE KEY `uk_event_subscriber` (`event_id`, `subscriber_id`)
--          └──────┬───────┘     └──────────┬──────────┘
--           索引的名字（自己起）      真正生效的字段（联合）
```

| 部分 | 含义 |
|---|---|
| `UNIQUE` | 约束类型：唯一（不允许重复） |
| `KEY` | 建的是索引 |
| `uk_event_subscriber` | **索引名**，`uk_` 是命名前缀，**不是语法关键字** |
| `(event_id, subscriber_id)` | 参与索引的字段，多个 = 联合索引 |

**前缀约定（团队习惯，业界通用）**

| 前缀 | 含义 | 本项目例子 |
|---|---|---|
| `pk_` | 主键 | `PRIMARY` |
| `uk_` | unique key，唯一索引 | `uk_app_key`、`uk_biz_no` |
| `idx_` | index，普通索引 | `idx_channel_time` |
| `fk_` | foreign key，外键 | 本项目未使用 |

**为什么不直接写字段名？**

1. 字段名要写在**括号里**，括号外那个位置是**索引名**，两回事；
2. 不写名字 MySQL 会**自动用第一个字段名当索引名**（如 `event_id`），
   以后同一字段再建索引就重名冲突，且 `DROP INDEX` 时分不清删哪个；
3. 有名字才能一眼看懂用途 —— `uk_event_subscriber` 比 `event_id` 信息量大得多。

### 4.2 联合唯一键的语义：组合唯一，不是各自唯一

以 `uk_event_subscriber(event_id, subscriber_id)` 为例：

| event_id | subscriber_id | 是否允许 |
|---|---|---|
| `evt_001` | 1 | ✅ 第一条 |
| `evt_001` | 2 | ✅ **允许**（event_id 重复了，但组合不同） |
| `evt_002` | 1 | ✅ 允许 |
| `evt_001` | 1 | ❌ **冲突**（组合完全相同） |

**如果用错**：只写 `UNIQUE KEY (event_id)`，那么一个事件只能推给**一个**下游，第二个订阅者插不进去 —— 功能直接坏掉。

### 4.3 为什么要这样设计：数据库层兜底幂等

下游可能重复收到同一条消息（网络重试、我们主动重试、下游超时但实际已收到）。
与其在代码里写 `if (已存在) return;`（并发下不可靠），不如让数据库直接拒绝：

> **唯一索引是幂等的最后一道防线。**

代码里写 `先查再插`，两个并发请求都会查到"不存在"，然后都去插入 → 产生两条。
唯一索引则保证两个并发只能成功一个。

### 4.4 普通索引 vs 唯一索引

| | 普通索引 `KEY idx_xxx` | 唯一索引 `UNIQUE KEY uk_xxx` |
|---|---|---|
| 加速查询 | ✅ | ✅ |
| 允许重复值 | ✅ | ❌ |
| 作用 | 性能 | 性能 + **数据约束** |

### 4.5 最左前缀原则（联合**普通**索引要注意）

```sql
KEY idx_client_time (client_id, event_time)
```

| 查询条件 | 能否用上索引 |
|---|---|
| `where client_id = ?` | ✅ |
| `where client_id = ? and event_time > ?` | ✅ |
| `where client_id = ? order by event_time` | ✅ |
| `where event_time > ?` | ❌（必须包含最左字段） |

> `show columns` 里看到 `Key` 列：`UNI` = 唯一索引，`MUL` = 普通多值索引，`PRI` = 主键。

## 五、五个核心设计决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **流水表与聚合表分离** | 流水记"点"（追溯），聚合记"线"（统计）。查"播了多久"聚合表一个字段，只有流水则需配对聚合 |
| 2 | **`status` + `end_reason` 双字段** | 只知道"结束了"不够，要区分正常断开/超时/服务器重启/被拒 |
| 3 | **`detail` / `payload` 用 JSON** | 不丢原始报文；新增事件类型无需改表；出问题能原样回放现场 |
| 4 | **幂等靠数据库唯一索引** | 不引入 Redis/MQ，减少运维面与故障点；重启不丢消息；并发安全 |
| 5 | **不使用物理外键** | 互联网项目常见做法：外键带来插入顺序约束与锁开销，关联完整性由应用层保证（配合逻辑删除 `deleted`） |

## 六、状态机

### `biz_channel.status`
```
0 离线 ──(on_publish)──▶ 2 推流中 ──(on_stream_changed regist=false)──▶ 0 离线
```
`1 在线` 为预留态（当前"有流即推流中"）。

### `biz_stream_session.status`
```
1 进行中 ──┬─(正常断流)──▶ 2 正常结束  end_reason=NORMAL
           ├─(超时无心跳)─▶ 3 异常结束  end_reason=TIMEOUT
           └─(ZLM 重启)──▶ 3 异常结束  end_reason=SERVER_DOWN
```

### `biz_webhook_push_log.status`
```
0 待推送 ──成功──▶ 1 成功
        └──失败──▶ 2 待重试 ──(达上限)──▶ 3 死亡
```

### 台账错误码分段
```
0      成功
1xxx   参数类（DB 层不产生）
2xxx   业务类：2001 未注册流 / 2002 重复 / 2003 状态不允许
3xxx   上游类：3001 ZLM 调用失败 / 3002 ZLM 不可达
5xxx   系统类
```

## 七、数据量与索引策略

| 表 | 增长速率（单机演示） | 策略 |
|---|---|---|
| `biz_ledger` | 每路流约 4~6 条/次，最高频 | 按 `event_time` 建索引；数据量上来后按月分区或归档 |
| `biz_stream_session` | 每次推流 1 条 | 无压力 |
| `biz_webhook_push_log` | 每事件 × 订阅者数 | 靠 `idx_status_retry` 只扫待推送的，避免全表 |
| `biz_recording` | 每录像切片 1 条 | 无压力 |
| `biz_api_client` | 极少 | 无压力 |

**一个刻意的取舍**：`biz_webhook_push_log` 兼做队列，扫描条件是
`status IN (0,2) AND next_retry_time <= now()`，靠 `(status, next_retry_time)` 联合索引
直接命中，不需要全表扫描。
